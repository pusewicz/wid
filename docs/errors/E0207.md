# E0207: value may be nil

An optional value (`T?`) is used where a plain `T` is required: reading a
field, calling a method, doing arithmetic, or passing or assigning it as a
`T`. The compiler cannot prove it is not `nil` at that point. A `T?` must be
unwrapped before use. Checking a local for `nil` narrows its type, so after
the check the compiler treats it as a `T`.

When the optional came from a call assigned to a local, the help rewrites
that assignment as a `guard`.

## Example

```wid
struct Player
  hp: Int
end

def find_player(id: Int) -> Player?
  return nil if id < 0
  Player.new(hp: 100)
end

def main
  player = find_player(1)
  puts player.hp
end
```

```text
error[E0207]: `player` may be nil here
  --> main.wid:12:8
   |
12 |   puts player.hp
   |        ^^^^^^ `find_player(1)` returns `Player?`
help: unwrap it and handle the nil case
   |   guard player = find_player(1) else
   |     return
   |   end
   = see `wid explain E0207`
```

## How to fix

- `guard v = maybe else … end` unwraps for the rest of the scope. The `else`
  branch must leave with `return`, `break`, `next` or `panic`.
- `if v = maybe … end` binds the value inside that branch only.
- A `nil?` check narrows: after `return if player.nil?`, `player` is a
  `Player`. Narrowing works on locals, not fields; copy a field into a local
  first.
- `maybe || default` unwraps with a fallback, and `&.` chains through the
  optional: `hp = find_player(2)&.hp || 0`.
- If the value can never be nil, change its type from `T?` to `T`. Pointers
  are already non-nil unless written `^T?`.

```wid
struct Player
  hp: Int
end

def find_player(id: Int) -> Player?
  return nil if id < 0
  Player.new(hp: 100)
end

def main
  guard player = find_player(1) else
    puts "no player"
    return
  end
  puts player.hp
end
```
