# E0201: undefined name

The code uses a name that nothing in scope declares. In Wid the first
assignment declares a variable, so a misspelled name in a read is not
silently a new variable: it is an error. The message says what kind of name
was expected: a name, variable, method, constant, package or module. A name
an imported package doesn't declare reads "`geo` has no member `Missing`",
with the closest of the package's public names, or a list of them when the
package declares only a few. The same code reports an `overload` set that
lists a method that doesn't exist. When a declared name is close in
spelling, the help offers it. Inside a method of a type, that includes the
methods a call without a receiver reaches: the type's own, those its modules
mix in, those `extend` blocks add and those its `using` fields promote, so
`heall(1)` suggests `heal(1)`. Inside a method, a name that is a field of
`self`, read bare or called like a method (`hp()`), gets the fix to read it
with `@name` (`@on_hit(3)` for a field that holds a proc), and a misspelled
name close to a field's suggests `@name`. Among declarations, where a call
can only run a macro, an unknown name is an undefined macro.

## Example

```wid
def main
  counter = 1
  counter += 1
  puts countr
end
```

```text
error[E0201]: undefined name `countr`
 --> main.wid:4:8
  |
4 |   puts countr
  |        ^^^^^^ not found in this scope
help: a similar name exists: `counter`
  |   puts counter
  = see `wid explain E0201`
```

## How to fix

- Fix the spelling. The help shows the closest name in scope, if there is
  one.
- Assign the variable before reading it. A variable assigned inside an `if`,
  a loop or a block exists only until that block's `end`; assign it before
  the block to use it afterwards.
- For a name from another package, import the package and qualify the name:
  `import "./physics"`, then `physics.step(…)`.
- A method of a type is called on a value (`ball.update(dt)`). Only inside
  that type's methods does a bare name call it on `self`.
- Inside a method, read a field of `self` with `@name`: `@hp` means
  `self.hp`. A bare name is a variable or a method call, never a field.

```wid
def main
  counter = 1
  counter += 1
  puts counter
end
```

## A field read without `@`

```wid
struct Player
  hp: Int = 100
  def score -> Int = hp * 2
end

def main
  p Player.new.score
end
```

```text
error[E0201]: undefined name `hp`
 --> main.wid:3:22
  |
3 |   def score -> Int = hp * 2
  |                      ^^ not found in this scope
  = note: `hp` is a field of `Player`; a bare name in a method is a variable or a method call, never a field
help: read the field with `@hp`, which means `self.hp`
  |   def score -> Int = @hp * 2
  = see `wid explain E0201`
```

Inside a method, `@name` means `self.name`, and it reaches the fields that a
`using` field promotes too. A bare name never reads a field: it is a local
variable, or a call of a method of `self`. Assigning to a bare name, like
`hp = 3`, declares a new local variable and leaves the field alone. Calling
the field, `hp()`, gets the same fix, `@hp`; a field that holds a proc is
called with `@on_hit(…)`, which calls the proc the field holds. A name close
to a field's, like `hpp`, suggests `@hp`, and a call close to a proc field's,
like `on_hitt(3)`, suggests `@on_hit(3)`.

```wid
struct Player
  hp: Int = 100
  def score -> Int = @hp * 2
end

def main
  p Player.new.score
end
```

## An undefined macro among declarations

```wid
macro def describer(name: Symbol) -> Code
  quote do
    def describe -> String = "#{@#{name}}"
  end
end

struct Player
  hp: Int = 100
  describe :hp
end

def main
  p Player.new
end
```

```text
error[E0201]: undefined macro `describe`
  --> main.wid:9:3
   |
 9 |   describe :hp
   |   ^^^^^^^^ no macro with this name is in scope
   = note: a call among declarations runs a macro, and the declarations it generates take the call's place
help: a macro with a similar name exists: `describer`
   |   describer :hp
   = see `wid explain E0201`
```

A call among declarations runs a macro, and the declarations it generates
take the call's place. Fix the macro's name, or import the package that
defines it and qualify the call (`lib.describer :hp`):

```wid
macro def describer(name: Symbol) -> Code
  quote do
    def describe -> String = "#{@#{name}}"
  end
end

struct Player
  hp: Int = 100
  describer :hp
end

def main
  puts Player.new.describe
end
```

## A misspelled macro call in a method

```wid
macro def counter(name: Symbol) -> Code
  quote do
    #{name} = 0
  end
end

def main
  countr :hits
  hits += 1
  puts hits
end
```

```text
error[E0201]: undefined method `countr`
 --> main.wid:8:3
  |
1 | macro def counter(name: Symbol) -> Code
  |           ------- the macro `counter` is defined here
...
8 |   countr :hits
  |   ^^^^^^ not found in this scope
help: a macro with a similar name exists: `counter`
  |   counter :hits
  = see `wid explain E0201`
```

When the name is close to a macro's, the help offers the macro. The call was
probably meant to run it, so the variables its code would have declared
(`hits` here) aren't reported as undefined too; the same holds for a call
standing alone on a line with a symbol argument whose name is close to
nothing else. Fix the macro's name:

```wid
macro def counter(name: Symbol) -> Code
  quote do
    #{name} = 0
  end
end

def main
  counter :hits
  hits += 1
  puts hits
end
```

## A name a macro declared in an operand

```wid
macro def parsed(name: Symbol, text: Code) -> Code
  quote do
    #{name} = #{text}.size
    #{name} > 0
  end
end

def main
  input = "42"
  ok = input != "" && parsed(:digits, input)
  p ok, digits
end
```

```text
error[E0201]: undefined name `digits`
  --> main.wid:11:9
   |
10 |   ok = input != "" && parsed(:digits, input)
   |                               ------ `parsed` declares `digits` here, but only for the right side of `&&`
11 |   p ok, digits
   |         ^^^^^^ not found in this scope
   = note: the code a macro generates in the right side of `&&` runs only when the left side is true, so the names it declares are visible only there
help: to use `digits` here, call `parsed` as a statement of its own before this line, so its code always runs
   = see `wid explain E0201`
```

A macro's code runs in place of the call, so the names it declares usually
stay visible after it. In an operand that doesn't run once with the statement
around it (the right side of `&&` or `||`, the value of `||=` or `&&=`, the
arguments of a `&.` call, a `when` pattern after a `case`'s first,
`type_info`'s operand or a loop condition), its code runs with the operand,
and the names belong to the operand. Call the macro as a statement of its own
to keep them:

```wid
macro def parsed(name: Symbol, text: Code) -> Code
  quote do
    #{name} = #{text}.size
    #{name} > 0
  end
end

def main
  input = "42"
  long = parsed(:digits, input)
  ok = input != "" && long
  p ok, digits
end
```

## A variable the macro's code can't see (hygiene)

```wid
macro def bump -> Code
  quote do
    count += 1
  end
end

def main
  count = 0
  bump()
  p count
end
```

```text
error[E0201]: undefined variable `count`
 --> main.wid:3:5
  |
3 |     count += 1
  |     ^^^^^ `bump`'s code can't see the caller's `count`
 ::: main.wid:8:3
  |
8 |   count = 0
  |   ----- the caller's `count` is declared here
 ::: main.wid:9:3
  |
9 |   bump()
  |   ------ `bump` expands here
  = note: a macro's code keeps the variables it declares apart from the code around the call, and can't see that code's variables either (hygiene); names spliced in from the call belong to the caller
help: to use the caller's variable, pass its name: take a parameter like `name: Symbol`, write `#{name} += 1` in the `quote`, and pass `:count` to `bump`
  = see `wid explain E0201`
```

A macro's code keeps the variables it declares apart from the code around
the call, as if each expansion renamed them, so the two never clash. That
works both ways: the `quote`'s own code can't see the caller's `count`, and
the caller can't see a variable the `quote` declares (the error then points
at it and says it is private to the expansion). Names spliced in from the
call belong to the caller, so pass the variable's name as a `Symbol` and
splice it:

```wid
macro def bump(name: Symbol) -> Code
  quote do
    #{name} += 1
  end
end

def main
  count = 0
  bump :count
  p count
end
```

A name in a `quote` that is one of the macro's own parameters gets the same
error, with the fix that splices it (`e * 2` becomes `#{e} * 2`): the
parameter holds the argument while the macro runs, and the code the `quote`
builds runs later, where the call is.

## A splice in a nested `quote`

```wid
macro def outer(n: Int) -> Code
  quote do
    macro def inner -> Code
      quote do
        #{n} + 1
      end
    end
  end
end

outer(3)

def main
  p inner()
end
```

```text
error[E0201]: undefined name `n`
  --> main.wid:5:11
   |
 5 |         #{n} + 1
   |           ^ splices in `inner`'s `quote` read `inner`'s names
  ::: main.wid:1:17
   |
 1 | macro def outer(n: Int) -> Code
   |                 - `n` is a parameter of `outer`
  ::: main.wid:11:1
   |
11 | outer(3)
   | -------- `outer` expands here
   = note: a splice belongs to the innermost `quote` around it: this one runs when `inner` runs, after `outer` has finished, so `outer`'s parameters are gone
help: generate a constant in `outer`'s `quote`, like `N_VALUE = #{n}`, and use `N_VALUE` in `inner`; or splice the value into `inner`'s own code, outside its `quote` (`v = #{n}`), and splice `#{v}` there
   = see `wid explain E0201`
```

A splice belongs to the innermost `quote` around it. `outer`'s code leaves
`inner`'s `quote` as written, and its `#{n}` runs when `inner` runs, after
`outer` has finished, so it reads `inner`'s names. Pass the value on through
a constant that `outer` generates:

```wid
macro def outer(n: Int) -> Code
  quote do
    N_VALUE = #{n}
    macro def inner -> Code
      quote do
        N_VALUE + 1
      end
    end
  end
end

outer(3)

def main
  p inner()
end
```

## `attr_reader`, `attr_writer` and `attr_accessor`

Ruby exposes a field through accessor methods. Wid has no accessor macros:
fields are always public, so code reads and writes them directly, and a
method can't share a field's name (E0202).

```wid
struct Hero
  hp: Int = 100
  attr_accessor :hp
end

def main
  hero = Hero.new
  hero.hp -= 10
  puts hero.hp
end
```

```text
error[E0201]: undefined macro `attr_accessor`
 --> main.wid:3:3
  |
3 |   attr_accessor :hp
  |   ^^^^^^^^^^^^^ no macro with this name is in scope
  = note: a call among declarations runs a macro, and the declarations it generates take the call's place
  = note: Wid has no accessor macros: fields are always public, and code reads and writes them directly
help: remove the call and use the field itself, like `hero.hp` or `@hp` in a method
  = see `wid explain E0201`
```

Remove the call. `hero.hp` reads the field and `hero.hp = 3` writes it:

```wid
struct Hero
  hp: Int = 100
end

def main
  hero = Hero.new
  hero.hp -= 10
  puts hero.hp
end
```
