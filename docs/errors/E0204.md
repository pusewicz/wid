# E0204: no such field or method

The value's type has no field or method with this name. Members are resolved
at compile time from the type's declaration, its `using` fields, its included
modules and any `extend` blocks for it. When the name is close to a member's
name, the help suggests it. When it is a common name from another language,
such as `length`, `count` or `to_string`, the help gives the Wid name.

The same code reports related member mistakes:

- an enum member that doesn't exist (`Dir.west`, `:west`), with the list of
  members;
- a type-level method (`def self.zero`) called on a value, or an instance
  method called on the type;
- a swizzle that reaches past the end of a small array, like `.z` on a
  `[2]F32`;
- `T.new` on a type that is not a struct or container;
- `@heal` or `@heal(1)` inside a method when `heal` is a method: `@name`
  reads a field and `@name(…)` calls the proc a field holds, while a method
  is called by name, so the fix writes `heal(1)`;
- a name that several `using` fields promote (see below).

## Example

```wid
struct Ball
  pos: [2]F32
  radius: F32 = 8.0
end

def main
  ball = Ball.new
  puts ball.radious
end
```

```text
error[E0204]: `Ball` has no field or method `radious`
 --> main.wid:8:13
  |
8 |   puts ball.radious
  |             ^^^^^^^ not found on `Ball`
help: did you mean `radius`?
  |   puts ball.radius
  = see `wid explain E0204`
```

## How to fix

- Fix the spelling. The help shows the closest field or method.
- Use Wid's names: `size` (not `length` or `count`), `nil?`, `to_s`, `to_i`
  and `to_f`, and `<<` to append to a dynamic array.
- Call a `def self.name` method on the type (`Ball.zero`) and an instance
  method on a value (`ball.update(dt)`).
- To add a method to a type you don't own, including builtin types, use
  `extend Type … end`.

```wid
struct Ball
  pos: [2]F32
  radius: F32 = 8.0
end

def main
  ball = Ball.new
  puts ball.radius
end
```

## Ambiguous `using` members

The same code reports a name that several `using` fields promote. Neither
field takes precedence, so the access has to say which one it means:

```wid
struct Body
  id: Int
  mass: F32
end

struct Sprite
  id: Int
  frame: Int
end

struct Player
  using body: Body
  using sprite: Sprite
end

def main
  pl = Player.new(Body.new(1, 2.0), Sprite.new(7, 0))
  p pl.id
end
```

```text
error[E0204]: `id` is ambiguous in `Player`
  --> main.wid:18:8
   |
18 |   p pl.id
   |        ^^ both `body` and `sprite` provide `id`
   = note: `using` promotes the members of several fields here, and more than one has this name
help: name the field to read it through, like `.body.id`
   |   p pl.body.id
   = see `wid explain E0204`
```

With three or more such fields, the label lists them all: "`body`, `sprite`
and `shape` all provide `id`". Write `pl.body.id` or `pl.sprite.id`. A field
or method declared on `Player` itself always wins over promoted ones, so you
can also add a `def id` that picks one. Inside a method of `Player`, a bare
`id`, a call `id()` and `@id` are ambiguous the same way, and the fix writes
`@body.id`.

## A member of a `Type` value

A `Type` value, such as a `t: Type` parameter, answers only `.name`, `.size`,
`.align` and `.fields`. `.methods` works only where the type is known: on a
type written by name (`Ball.methods`) or on `Self`.

```wid
struct Ball
  r: F32
  def area -> F32 = @r * @r
end

def count_methods(t: Type) -> Int = t.methods.size

N = comptime count_methods(Ball)

def main
  p N
end
```

```text
error[E0204]: `Type` has no field or method `methods`
 --> main.wid:6:39
  |
6 | def count_methods(t: Type) -> Int = t.methods.size
  |                                       ^^^^^^^ not found on `Type`
  = note: a `Type` value answers only `.name`, `.size`, `.align` and `.fields`
  = note: `.methods` works on a type written by name, like `Vec2.methods`, and on `Self`
help: take the methods instead of the type: a `[]MethodInfo` parameter, given `Vec2.methods`
help: in a macro, call the macro in the type's body and read `Self.methods`
  = see `wid explain E0204`
```

Pass the methods, read from the type written by name, instead of the type.
In a macro, call the macro in the type's body and read `Self.methods`.

```wid
struct Ball
  r: F32
  def area -> F32 = @r * @r
end

def count_methods(methods: []MethodInfo) -> Int = methods.size

N = comptime count_methods(Ball.methods)

def main
  p N
end
```
